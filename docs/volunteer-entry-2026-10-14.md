# 志工填報修正與白化核對

## 2026-11-09 完整手板送出失敗修正（PRD 0.9.23、Schema v1.18）

- 原因：網頁僅列本版手板，原後端完整性卻要求所有啟用主檔（僅排除石斑魚另一模式／合計與罕見 Other）；歷史新增的 16 列魚類、刺棘海膽與未分病種疾病因此成為隱藏必填。原測試從全主檔補滿資料，漏掉實際前端送出路徑。
- 新增 `000023_entry_board_contract.sql` 的版本必要列對應；v4 只驗本版及所選模式，原主檔與歷史觀測保留，不以 0 補出額外列。`000022` 保持原檔，不修改已發布遷移。部署前需先套用所有尚未完成的前序遷移及 000023。
- 公開 config 新增 `entry_board`，志工頁由同一契約載入正式列，使用固定 `entry_row_id` 對舊草稿取值，排序改變不得錯配。載入失敗或必要項目停用時在過程顯示明確提示並阻擋送出，可重試；本機／debug 預覽清單不代表線上配置成功。
- 後端漏項訊息包含手板、項目及段次。HTTP 400／422 回到檢查頁並取消核對勾選，不再誤指網路；伺服器失敗與網路例外分開處理，均保留草稿。排除固定必要的罕見／衝擊列會在前端先提醒恢復並填 NA，不會等到資料庫才報錯。
- 新增實際 app.js payload → service → 隔離 PostgreSQL 儲存 → 逐值讀回 → 發布檢查；使用去識別化草稿及原始附件的唯讀測試入口，另驗兩種模式、主檔增加不擴充必填、必要漏項拒絕及回滾。測試不連線寫入實際資料庫，不重送客戶觀測。

## 2026-11-09 Belt 手板與送出前補零（最新決策，PRD 0.9.22）

- 輸入與最後核對的 Belt 表使用獨立可上下左右捲動區域；段次表頭固定在上緣，類群欄固定在左緣，交會的第一格在最上層。表格不撐出整頁水平捲動。
- 「是否將空格都填入零？」由各手板上方移到最後檢查的送出按鈕旁；平板並列、手機換行。一次列出此次所選魚類／無脊椎／罕見生物適用列的各表空格數，二次確認才補值，取消不修改。既有數字、NA、未選方法、隱藏體長模式及排除列保留；底質與環境衝擊不補零。補值後更新合計與問題清單，取消核對勾選，不能沿用補值前的確認直接送出。
- 窗口確認本次為移動既有補零按鈕；缺值契約不變：確實調查但未發現為 0，未調查／未記錄為 NA。這次無資料庫結構異動，也未執行歷史轉檔或線上部署。

## 2026-11-09 白化 health_status 契約（最新決策）

- UI 標題與未選取按鈕使用「點選標記白化」，實心顯示「已標記白化」；空心只代表未標記。進入白化頁不自動將全部珊瑚格設為未白化；按「完成白化標記」後，才將其餘未標記的適用珊瑚格確認為 `not_bleached`。
- 新網頁以 `substrate_points[].health_status` 送出逐格原始狀態：`bleached`＝白化，`not_bleached`＝已確認未白化，`null`＝尚未確認／歷史未知／不適用。未白化不是整體健康診斷，不增加疾病等未定義選項。適用範圍維持表面 HC（含 a／b／c）與 SC，泥下合成代碼不自行擴充。
- 新增 migration `000022_substrate_health_status.sql`：建立 `substrate_point.health_status`、同步相容欄與約束、更新逐格統計及發布完整性檢查。遠端 `000021` 已用於恢復 OT 主檔數字碼，本批健康狀態欄位順延為 `000022`，不得重用已發布的遷移編號。`is_bleached` 保留相容，舊客戶端的明確布林可對應新欄；API 若兩欄衝突即拒絕。現有明確逐格布林可一對一轉入，NULL 不補值，不用原始分段總數推估位置，也不改寫歷史總數。
- 本機草稿改用 `healthStatus`；舊草稿的白化正值保留，舊自動負值只有在白化核對已完成時才承接。改底質後清除該點狀態，修改標記會取消先前最終核對勾選。最終統計區分已標記數與待確認格數。
- 本節取代先前以 `is_bleached` 作為唯一原始欄位與「空心＝無白化」的舊說明。PRD 0.9.21、Schema v1.17 已同步；部署需先套用 `000022` 再上新版程式。本次不更新線上資料庫，也不重跑歷史轉檔。

## 舊資料證據與本次決策

讀取 2026-09-29 confirmed-only 匯入包的 2,620 筆分段白化紀錄（655 個來源檔），找出 83 筆非零紀錄、共 44 份來源。逐份讀取原 XLS／XLSX 的 DATA、說明、比例公式及表面測點；44 份白化數量均未超過對應 HC／SC 點數。

例如龍洞北 5 m 的 2022-08-18 原檔，DATA!X37 公式以 X35 的 HC 白化數量除以第一子樣區底質 HC 的 COUNTIF。美人洞 2021-10-20 淺場原檔 DATA!X35 為 1、DATA!B42 的 HC 點數為 6，DATA!X37 為 16.6667%；DATA 第 12 列另註記白化以顏色區隔。以上支持本次新填報以「白化測點」定義自動加總。

部分舊檔 SC 白化比例公式在第三、第四子樣區誤用 HC 作為分母。因此只用原始數量與測點核對定義，不照抄舊比例公式；新系統按 HC／SC 各自的測點重算，HC-a／b／c 明確合併到 HC。

完整機器可讀證據：[bleaching_evidence.json](../../outputs/volunteer_entry_2026-10-14/bleaching_evidence.json)。這是定義核對，不是全量數值再轉檔；原始資料與既有匯入包沒有修改。

## 現在的輸入流程

活動代碼驗證 → 選擇探查 → 共用資訊及模式 → 每五格輸入原始數字 → 整張手板核對 → 表格點選白化位置 → 自動加總各區 HC／SC → 補充 RKC／其他損害說明 → 最後原始數字／轉換代碼核對 → 儲存待審核。

- 每五格切換由使用者決定；原始數字不立即轉成英文。
- 左側呈現當前單欄 20 點，右側五格輸入；數字核對、白化與最後核對均依原手板表格排列。
- 新填報用 `substrate_point.is_bleached` 保存每格，`substrate_bleaching_point_summary` 自動加總。歷史 `substrate_bleaching` 原始數量保留，沒有逐格資料的舊紀錄維持 NULL；不重複輸入新總數。
- RKC 以非 NA 有效點為分母，達 10%（含）需填原因；與一般 comments 分欄。
- 其他珊瑚損害任一區大於 0 時需獨立說明。
- 魚類分體長／不分體長切換只輸出選中模式，舊模式值保留於草稿；硬珊瑚型態先選擇是否分類。
- 罕見生物其他列保留名稱、四段數量、選填尺寸與備註。
- 天氣、氣溫及經緯度暫以選填保留；座標需成對。

## 活動代碼與資料庫契約

管理端新增 `/reef-activities.html`，提供建立、停用、重新產生。代碼為 128-bit 隨機值，資料庫僅存 SHA-256；新代碼只回傳一次，操作寫入專用 audit。可限制樣點、日期，失效時間選填。志工端以 POST 驗證，正式送出再次由伺服器檢查範圍；本機 debug 提供測試活動，不會呼叫儲存 API。

新送出格式 `reefcheck-web-v4`，新增 `activity_code`、`entry_metadata`、`rkc_bleaching_note`、`other_damage_note`、`bleaching_mode`、transect `coral_morphology`，及 rare observation `observed_size`／`notes`。後端保存原始欄位、NA 狀態、draft metadata；同一氣瓶的重複新送出不會覆寫既有來源。

2026-10-19 已整合遠端的公開展示、發布審核及完整手板檢查。新增 migration 順延為 `000014_point_bleaching.sql`、`000015_volunteer_entry_details.sql`、`000016_point_bleaching_contract.sql`，不改動遠端已存在的 000008–000013。魚類體長模式沿用資料庫 `fish_size_mode`，API 的 `fish_length_mode` 會核對後對應同一欄位；發布狀態及缺值原因統一以 `event` 為準，不在 metadata 另存第二份。白化統計依送出版本選用逐格標記或歷史原始總數，發布檢查不要求新填報重填手動白化附表。

本次未對既有資料庫套 migration，也未手動部署。沒有本機 PostgreSQL 測試連線時，資料庫回歸會略過，不能視為正式活動／資料庫往返已驗證。

## 驗證

前端測試涵蓋五格位置與整張 160 點對應、debug 空白跳關、兩種模式值隔離、各區 HC／SC 自動計數、10% 邊界與 NA 分母、條件式備註、rare metadata、活動樣點範圍。Go 測試涵蓋完整 160 點、段次座標、逐格白化完整性、記錄者與模式、日期／樣點／有效期；另提供資料庫回歸，確認既有手填總數不被逐格計數覆寫。沒有 PostgreSQL 測試連線時，資料庫回歸會明確略過，不能視為資料庫驗證成功。

## PRD 補充：活動建立、歷史發布與管理者核對（2026-11-02）

### 活動代碼

- 管理者從「Reef Check 資料 → 活動代碼管理」建立填報活動，必填名稱、開始／結束日期、允許樣點，可選填代碼失效時間。
- 建立成功即產生一組活動代碼，畫面顯示供窗口保存及交給志工。資料庫只保存雜湊；遺失時重新產生，舊代碼立即失效；停用後拒絕驗證和送出。
- 志工先輸入代碼；驗證成功帶入活動名稱、日期範圍及可用樣點。僅一個樣點時直接帶入，多個時由志工選擇；實際調查日期仍需確認。
- 伺服器在最終送出時再次驗證代碼、有效期、樣點與日期範圍，不能只靠前端限制。資料保存活動關聯，供管理者核對。
- 「公開內容 → 活動」為公開活動介紹；填報活動及其代碼在獨立管理頁建立，兩者目前沒有自動建立關係。
- 驗收：建立後可用代碼載入活動；無效、過期、停用或已換發代碼不能填報；跨樣點／跨日期送出被拒絕；志工新紀錄維持草稿待核對。

### 發布規則

- 經確認的歷史 CSV 匯入資料新增時直接為 `published`，公開查詢可立即取得；一般手動建立和志工填報仍為 `draft`。
- 既有 726 筆以原始 `event.csv` 識別碼清單批次發布，不需逐筆按鈕。只更新清單內、沒有網頁送出快照、沒有活動填報關聯、沒有人工發布操作紀錄的草稿；已發布、封存與人工決定的草稿保留。
- 批次操作寫入發布 audit，在交易內完成，支援 dry-run；不以缺少來源標記為由全庫發布。

### 核對介面

- 預設顯示樣點、日期、時間、深度、活動、缺值原因，各調查的記錄者、水溫、能見度及備註。
- 底質依手板呈現四個子樣區，每區左／右欄各 20 點，位置間隔 0.5 m；可水平捲動，並列數字及代碼、白化標記；泥下底質另列。
